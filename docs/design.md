# treadcraft 初期設計

作成日: 2026-09-14 / 状態: 設計案。実装・実データ接続は未実施。

名称はユーザー指定の `treadcraft` を使用する。作業ディレクトリの `threadcraft` とは綴りが異なるため、公開時の名称・アプリ識別子は実装開始時に確定する。

## 1. 目的と範囲

AI コーディングのスレッドを、RTS の部隊編成のように自分の判断でまとめるデスクトップアプリ。分類は会話のコンテキストや作業ディレクトリを変更しない。

対象 OS は macOS・Windows・Linux。最初の接続先はローカル Codex とする。ただし、Codex CLI とデスクトップアプリのどのスレッドを取得できるかは第1反復で検証する。通常の ChatGPT 会話や Zed 独自の履歴まで取得できるとは仮定しない。

### MVP

- 左: 未分類スレッドを作成日時の降順で表示。古いスレッドもスクロールで参照できる。
- 右: ユーザーが作成したグループと所属スレッドを表示。
- グループの作成・名前変更・削除。
- ドラッグ＆ドロップで分類、別グループへの移動、未分類への戻し。
- 再起動後も分類を保持。
- タイトル検索、手動更新、接続状況・最終同期日時の表示。
- ドラッグを使わない「移動先を選ぶ」操作。

### MVP の仮定

- スレッドは最大1グループに所属。RTS に似た操作感を目指すが、複数部隊への重複所属は初版に含めない。
- グループ内のスレッドとグループ自体は手動で並べ替え可能。
- 未分類の「直近」は作成日時順であり、更新日時順ではない。同時刻は ID 順で安定化する。
- グループの削除は分類の解除だけ。会話を削除・アーカイブしない。
- アーカイブ済みスレッドは標準表示から除外するが、保持済みの所属情報は消さない。

### 対象外

会話の送受信、エージェント実行・停止、会話本文の編集、クラウド同期、他人との共有、自動分類、複数選択、RTS の数字キーによる編成、階層グループ。会話を元アプリで開く操作は、サポートされた起動手段を確認してから追加する。

## 2. 画面と操作

```text
┌ treadcraft ──────────────────────────────────────────────┐
│ [タイトル検索                         ] [更新] [設定]     │
│ 接続済み · 最終同期 18:40                                 │
├──────────────────────┬───────────────────────────────────┤
│ 未分類 (12)           │ グループ              [+ 作成]     │
│ 新しい順              │                                   │
│ ┌ API 調査 ─────────┐ │ ▼ リリース準備 (3)          [⋯]  │
│ │ 作成時刻・作業場所 │ │   修正 A                           │
│ └───────────────────┘ │   テスト B                         │
│   UI 改善             │   リリース手順                     │
│   不具合調査          │                                   │
│                      │ ▼ 調査メモ (0)              [⋯]  │
│ [ここへ戻して分類解除]│   [スレッドをドロップ]             │
└──────────────────────┴───────────────────────────────────┘
```

- グループは折りたたみ式の縦一覧。空・折りたたみ状態でもヘッダーをドロップ対象にする。
- ドロップ先と挿入位置を強調。領域外や Escape で中止し、分類を変えない。
- 折りたたまれたグループへのドロップは末尾に追加する。
- 削除確認に「所属する N 件は未分類に戻ります。会話は削除されません」と表示する。
- タイトル欠落時は「無題のスレッド」、作業場所不明時は「不明」と明示する。
- 検索は両ペインのタイトルに適用。検索中は分類移動のみ許可し、隠れた項目を含む並べ替えは無効化する。
- 初回読込中、未分類なし、グループなし、検索結果なし、接続失敗を別の状態として扱う。
- オフラインでは取得済み一覧とローカル分類を利用可能。「最新ではない」ことを表示する。
- キーボードでカード選択→移動メニュー→グループ選択。色だけで状態を伝えず、日本語 IME 入力中の Enter では確定処理を走らせない。

## 3. 構成

採用案: Tauri 2 / React + TypeScript / Rust / SQLite。パッケージの細かな選定・バージョン固定は実装時に行い、今回は追加しない。

```text
React UI
  │ 型付き Tauri commands / 変更通知
Rust アプリケーション層
  ├─ 分類サービス ── SQLite（分類の正本・スレッドのキャッシュ）
  └─ 同期サービス ── Codex アダプター ── App Server（stdio）
```

### 責務

| 層 | 担当 | 担当しないこと |
| --- | --- | --- |
| UI | 表示、検索、ドラッグ操作、入力検証補助 | SQL 実行、ファイル探索、CLI の直接起動 |
| 分類サービス | 所属制約、並べ替え、削除、トランザクション | Codex の会話変更 |
| 同期サービス | ページ取得、キャッシュ更新、再接続 | 同期結果によるローカル分類の上書き |
| Codex アダプター | 初期化、リクエスト対応付け、レスポンス変換 | 内部 DB の直接更新 |
| SQLite | 分類とキャッシュの永続化 | Codex の認証情報のコピー |

Tauri と Rust のスキルを踏まえ、UI と I/O を分離し、失敗を型付きエラーとして返す。DB アクセスは専用ワーカーで直列化し、ロックを保持したまま非同期通信を待たない。

### Codex との接続方針

- ユーザーが導入済みの Codex CLI を使用する案を第一候補とする。未導入・未対応バージョン・パス不明を設定画面で扱う。CLI の同梱は別途判断する。
- Rust がアプリ専用の App Server 子プロセスを管理し、stdio で接続する。既存デスクトップアプリの内部ソケットへ無断接続する設計にはしない。
- 初期化ハンドシェイク、タイムアウト、要求 ID と応答の対応、stderr の排出、再接続時の未完了要求の失敗処理を持つ。
- アプリ終了時に自身が起動した子プロセスだけを終了・回収する。他の Codex プロセスを停止しない。
- 初回・手動更新・フォーカス復帰時に一覧を照合する。前景中の定期更新は暫定30秒、重複実行なし、失敗時はバックオフ。実測で調整する。
- 通知やフックは再取得のきっかけとして扱う。別クライアントの全スレッド変更が通知されるとは仮定しない。
- 一覧取得目的で `thread/resume` を全件に実行しない。会話本文・認証情報は取得対象に含めない。

App Server の接続方法・初期化・スレッド API は [公式ドキュメント](https://learn.chatgpt.com/docs/app-server) を参照する。実際の対応範囲は導入済み CLI のスキーマと疎通結果で決める。

## 4. 分類の保存先の判断

推奨する初期案は **treadcraft 独自のローカル分類**。Codex 側の構成を変えず、切断中にも整理でき、将来の接続先追加にも対応しやすいため。

ただし、調査した Codex CLI 0.153.4 の生成スキーマには以下が存在した。

| メソッド / フィールド | スキーマ上の役割 |
| --- | --- |
| `threadSection/list` | セクションの一覧取得 |
| `threadSection/create` | 名前付きセクションの作成 |
| `threadSection/update` | 名前・外観の更新 |
| `threadSection/delete` | セクションの削除 |
| `thread/section/move` | スレッドの移動、順序指定、`sectionId: null` で解除 |
| `thread/list` の `sectionId` | セクションによる絞り込み |

これは API 定義の存在を確認しただけで、実際の利用可否、安定性、Codex UI との相互反映、削除時の振る舞いは未確認。「Codex にグループ機能がない」とは断定できない。

MVP ではローカル分類と Codex セクションを混ぜない。左の「未分類」は treadcraft の所属がないスレッドを指し、Codex の `sectionId` によって取得対象を除外しない。Codex 側にも分類を反映する要望が出た場合は、別反復でセクション API を隔離環境で検証し、正本をどちらに置くか決め直す。自動二重書き込みは行わない。

## 5. データ設計（概念モデル）

| エンティティ | 主な属性・制約 |
| --- | --- |
| Source | id、種類、接続先識別子、表示名、同期状態、最終成功日時 |
| ThreadCache | source_id + thread_id を複合主キー、タイトル、作成・更新日時、作業場所、アーカイブ状態、最終観測日時 |
| Group | UUID、名前、表示順、作成・更新日時 |
| Membership | source_id + thread_id を一意にし、group_id、グループ内表示順を保持 |
| AppState | スキーマバージョン、分類リビジョン、表示設定 |

- グループ名は前後空白を除去し、空文字を拒否する。長さ上限は100文字、同名は許可し ID で識別する。
- SQLite の外部キー制約を有効にする。グループ削除で Membership のみを削除し、ThreadCache は残す。
- 移動・並べ替え・グループ削除はそれぞれ1トランザクション。初版の順序は整数で保持し、対象リストだけ振り直す。
- 同期が途中で失敗しても、未取得のスレッドを削除しない。完全な列挙でも単発の欠落から元データ削除を断定しない。
- ThreadCache は再構築可能だが、所属はユーザーデータ。キャッシュ欠落時にも所属情報を捨てず、必要なら取得不能のカードとして保持する。
- 保存先は OS 別アプリデータディレクトリ。スキーマ移行はバージョン管理し、既存分類の保全をテストする。
- タイトル・作業場所は機密情報を含み得る。ログに本文、トークン、フルパス、タイトルを既定で出さない。DB のアプリ独自暗号化は初版対象外とし、ローカル保存の性質を説明する。

## 6. UI と Rust の境界

以下はアプリ独自 IPC の設計案であり、既存コードの API ではない。

| コマンド | 結果 / 振る舞い |
| --- | --- |
| `get_board` | ペイン表示用データ、分類 revision、同期状態 |
| `create_group` / `rename_group` | 検証済みグループを永続化 |
| `delete_group` | グループ削除と所属解除を原子的に実行 |
| `move_thread` | 移動先 nullable group ID と挿入先 thread ID を受け取る |
| `reorder_group` | 指定グループの表示順を変更 |
| `refresh_threads` | 同期を要求し、実行中ならまとめる |
| `get_connection_status` | CLI 利用可否、対応状況、接続エラー |

分類の更新は `expectedRevision` を受け取り、古い操作には `Conflict` を返して再取得する。同期は分類 revision を変更しない。コミット済みレスポンスを正とし、イベントは再取得通知に限定する。

初版はドラッグ中だけプレビューし、ドロップ後は対象を処理中表示にして永続化を待つ。同じ対象への連続操作は完了まで抑止する。失敗時は元の位置と所属を維持して通知する。

エラーは `Validation` / `NotFound` / `Conflict` / `Storage` / `SourceUnavailable` / `UnsupportedVersion` に分類。IPC の JSON 命名は明示的に camelCase に揃える。

権限はメインウィンドウに必要なものだけを付与する。WebView に任意シェル・任意 SQL・広範囲ファイルアクセスを公開しない。独自 command 側でも入力・呼出元を制限し、プラグイン権限だけで安全とみなさない。[Tauri capabilities](https://v2.tauri.app/security/capabilities/) を実装時に確認する。

## 8. 原因仮説（新規開発のため連携仮説・暫定）

**仮説:** 対象とするローカル Codex 環境を参照する App Server の `thread/list` により、ユーザーが整理したい既存スレッドの安定 ID と表示用メタデータを取得できる。

根拠は API スキーマの存在であり、実データとの一致はまだ証明していない。デスクトップと CLI の保存領域・取得対象が異なる、または state DB のみでは目的のスレッドを取得できない場合、この仮説は対象範囲について成立しない。

最初の反復で解消する証拠不足は「既存の対象スレッドを列挙できるか」の1点に限定する。通知、ネイティブ分類 API、ドラッグ操作の検証は混ぜない。

## 9. 第1反復の調査対象

### 必要な観測

対象クライアントと保存環境、代表的な既存スレッドの一致、安定 ID、作成日時、ページング、取得範囲の制約、必要な CLI バージョン。

### 最小の手順（計画・未実行）

1. 対象を現在利用中のローカル Codex 環境に限定し、保存環境の識別だけを確認する。認証ファイルや会話本文は出力しない。
2. App Server を stdio で起動して初期化する。既存のユーザー設定・フックは変更しない。
3. `thread/list` を `useStateDbOnly: true`、非アーカイブ、作成日時降順で呼ぶ。作業場所・プロジェクト・セクションによる絞り込みはしない。sourceKinds の既定値を暗黙に信頼せず、対象クライアントに対応する種類をスキーマから選んで記録する。
4. cursor がなくなるまで列挙し、ID で重複排除する。ページエラーを完全な一覧と扱わない。
5. ユーザーが対象としている代表スレッドと結果を照合する。報告には件数・一致可否だけを残し、タイトルや作業場所は必要以上に保存しない。
6. 再接続して ID とメタデータを再取得し、子プロセスの終了・回収も確認する。

### 判断基準

- 採用: 対象の代表スレッドを安定 ID 付きで取得でき、必要なメタデータと取得範囲を説明できる。
- 部分採用: CLI のみ等の制約が判明した場合、対応範囲を明記する。ユーザーが想定した対象を欠くなら、了承前にそれを製品仕様に固定しない。
- 不採用・再計画: 対象スレッドを取得できない、内部 DB 書換えが必要、またはデータ取得の正当な手段を確認できない。

## 10. 検証方法

### 第1反復

- 計画: `codex app-server --listen stdio://` を調査用クライアントから起動し、初期化・一覧取得・終了を観測する。起動コマンド単独では検証完了ではない。
- 計画: 上記のページング・代表スレッド照合・再接続チェック。調査用クライアントはまだ存在しないため、架空の npm スクリプトを実行済みとして記載しない。
- 計画: 結果を接続環境、CLI バージョン、取得対象、成功・失敗条件とともに設計へ追記する。

### 実装後に設ける受け入れ条件

- 未分類→A→B→未分類と移動しても重複せず、再起動後も所属が一致する。
- 所属付きグループを削除すると全件が未分類へ戻り、元の会話は変わらない。
- 保存失敗、古い revision、移動中の対象グループ削除で分類が破損しない。
- ページ途中の同期失敗や一時的な取得漏れでも分類を失わない。
- 接続中断・再起動・アプリ終了時に処理待ちや所有子プロセスを残さない。
- macOS・Windows・Linux それぞれで内部ドラッグ、キーボード代替、日本語入力、保存先、CLI 検出、配布ビルドを確認する。macOS 上の成功だけで全 OS 対応済みとはしない。

将来の Rust 検証コマンド候補は `cargo test`、`cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`（すべて計画、Cargo プロジェクト作成後）。UI のテスト・lint・型チェックは採用ツールと package.json を確定してから正確なコマンドを記録する。

## 11. 制約・リスクと後続反復

- 今回は設計文書だけを追加。依存追加、アプリ実装、Git 初期化、フック導入、外部データ変更は行わない。
- 既存 Codex の内部 DB を直接更新しない。診断でもメタデータ修復を伴う経路へ自動で切り替えない。
- 初期化による通常のプロセスログ等はあり得るが、調査中に会話作成・再開・削除やセクション更新は行わない。
- 取得漏れを設定とページングで説明できなければ、第1反復を打ち切って不足する証拠と選択肢を報告する。JSONL 全文収集や認証情報複製に範囲を拡張しない。
- App Server の変更への追従が必要。最低対応バージョンと未対応時の表示を実測で決める。
- Tauri は OS ごとの WebView を使う構成であり、UI の動作や配布要件には OS 差がある。署名・公証・Linux 配布形式はリリース設計で別途決める。

第1反復が成立した後の候補。各反復の詳細は、その直前の結果に基づいて作成する。

1. 分類の整合性: ローカル永続化で「移動・グループ削除が会話を失わせない」を検証。
2. 操作の成立: 固定データによる2ペインで、ドラッグとキーボード操作が同じ結果になることを検証。
3. 実データ統合: 検証済み Codex 一覧を同期し、再取得でも分類が保持されることを検証。
4. 同期の堅牢性: 切断・再接続・他クライアントの変更を扱い、必要なら通知を補助として追加。
5. クロスプラットフォーム: 各 OS の実行・配布を検証。

ネイティブセクション連携、会話を開く操作、RTS 型ショートカットは、それぞれ必要性と根拠を確認して別の反復にする。
